# Android API coverage

Every public class, method and field of the Android API, at every API level from 1 to 36, with what a converted app
gets for it. The per-package lists are in [`api/`](api/); totals are below. Both are generated by
`tools/apireport.sh ANDROID_JAR [api-versions.xml]`, which resolves each member the way the linker resolves an app's
references (same providers, renames and redirections).

## API levels

The list is the union of all API levels: the SDK's `api-versions.xml` (AOSP `prebuilts/sdk` commit `3af7c935`, API 1
to 36), plus the overrides API 35's `android.jar` declares. Each class and member carries the levels it exists at:

* `[API 9+]`: added in API 9, still present.
* `[API 1-22, removed in 23]`: removed from the SDK in API 23 (for example the Apache HTTP client). Apps built for
  older levels still call these, so they are listed.
* `, deprecated in N`: deprecated from level N (still callable).

A converted app sees one level: `Build.VERSION.SDK_INT` is `max(19, minSdkVersion)` (or `--sdk N`), and resources are
resolved for it. There is one framework for all levels: whether a member is implemented does not depend on the level
the app sees.

## Differences between levels

Members that differ between levels do not conflict at link time, and behaviour that differs is chosen by the app's
level:

* **Signatures.** Dex code calls a method by class, name, parameter types and return type, and the linker resolves
  calls the same way. A member that changed between levels is two members; an app finds the one its SDK declared.
  Overloads added at later levels are separate members as well. The same name and parameters with a different return
  type is legal in bytecode (not in Java source): `javac` writes such pairs as bridge methods for covariant overrides.
  The framework is compiled by `javac` and TeaVM's class library keeps both forms, so `ByteBuffer.flip()` resolves
  whether the app was compiled against Java 8 (returns `Buffer`) or Java 9+ (returns `ByteBuffer`). The pairs in the
  Android API, and any descriptor the runtime lacks while it has the same method with another return type, are listed
  below; the remaining ones are in TeaVM's class library (its `java.time` is ThreeTen's, whose `Period.getChronology()`
  and `IsoChronology.period()` return the general types; its `LogRecord.getThreadID()` returns `long`).
* **Removed members.** The list, and the linker, keep members removed at later levels, so an app built for an old level
  still finds what it calls (`org.apache.http`, removed in 23).
* **Behaviour.** There is one implementation of each member. Where Android's behaviour depends on the level, the
  runtime follows Android's rule for the app's levels: `Build.VERSION.SDK_INT` is the device level (above); resources
  with `-vN` qualifiers are chosen for it; the default theme follows `targetSdkVersion` like
  `Resources.selectDefaultTheme` (`Theme` below 11, `Theme.Holo` below 14, `Theme.DeviceDefault` below 24, then
  `Theme.DeviceDefault.Light.DarkActionBar` if the device level is 24 or higher); `ApplicationInfo.targetSdkVersion`,
  `minSdkVersion` and `VMRuntime.getTargetSdkVersion()` report the manifest's values (target defaults to min), which
  AndroidX and other libraries use for their own switches. Device policies tied to the target level are not modelled:
  permissions are always granted, and there are no background or storage restrictions.
* **Constants.** `javac` and `d8` copy constant values into the app, so a constant keeps the value of the SDK the app
  was compiled with.
* **Library copies.** A class the app carries that the platform also has (`org.json`, `org.xmlpull`, `android.*`) is
  dropped: the platform's copy wins, as Android's boot class path comes before the app. The Apache HTTP client follows
  Android's rule for the device level: up to 27 it is on the boot class path, and from 28 only for apps that declare
  `<uses-library android:name="org.apache.http.legacy"/>`. In those cases the bundled 4.0 client wins over a copy in
  the app; otherwise the app's copy wins and the bundled client only supplies classes the app lacks.

## Legend

| Mark | Meaning |
| --- | --- |
| `+` | Implemented: by the framework (`runtime/framework`, written or ported from AOSP), TeaVM's class library (`java.*`), a bundled library (`org.json`, kXML for `org.xmlpull`, Apache HTTP client 4.0 for `org.apache.http`), or a hand-written replacement (`a2w.jdk.*`, `a2w.xml.*`, `a2w.jdk.Compat`). Includes what a device without the hardware answers, in classes of [genapi-absent.txt](../tools/genapi-absent.txt) (`BluetoothAdapter.getDefaultAdapter()` is `null`). |
| `*` | Derived: a body `tools/genapi.sh` writes for a data class from its SDK shape: a getter returns the value its constructor, setter or builder stored; `equals`, `hashCode`, `toString`, `writeToParcel` and `CREATOR` cover those values. Validation and computed values are not modelled. |
| `~` | Present, but the body is empty, returns a constant or always throws: the call is accepted and has no effect, or always gets the same answer (`View.isInEditMode()` returns `false`, `Thread.stop()` throws as on Android). Empty callbacks (`onX`) count as `+`, since they are empty on Android too. |
| `-` | Missing. The linker generates a stub (or the class declared from the SDK has one) that logs `W/apk2web: not implemented: Class.method` once and returns a default: `0`, `false`, `null`, `""`, an empty array or collection, or `this` for builder-style methods. A missing constructor delegates to the closest existing one. |

A class marked "declaration" is declared from `android.jar`'s shape (`runtime/framework-gen`: superclass, interfaces,
constants, fields, nested classes, every member at every level); its bodies are stubs unless marked `*` or `+`.
Compile-time constants are not listed: `javac` and `d8` copy their values into the app. `[static]` marks static
methods (known for members present in API 35's `android.jar`).

`+` means the member has real code, not that it behaves exactly as on a device. Behavioural limits are listed in the
[README](../README.md#limits).
